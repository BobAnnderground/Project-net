# Fixnet — Software Requirements Specification (SRS)

**Версия:** 0.1 (черновик для прототипирования)
**Статус:** Прототип без интеграций — все данные и соединения мокаются
**Платформа:** Windows-приложение, окно 1200×800px

---

## 1. Введение

### 1.1 Назначение документа
Документ описывает функциональные требования, сущности, их атрибуты, состояния и взаимосвязи для приложения Fixnet — системы маршрутизации трафика на уровне отдельных сервисов (per-app routing), в отличие от классического VPN, работающего на уровне всего устройства.

Документ предназначен для генерации архитектуры и кода прототипа (без бэкенд-интеграций, без реального сетевого драйвера) с целью тестирования пользовательских флоу.

### 1.2 Область действия
Прототип реализует:
- UI/UX всех основных экранов;
- локальное (mock) состояние сущностей;
- имитацию сетевых событий (подключение, деградация, обрыв, переключение на аварийный мост);
- имитацию мониторинга в реальном времени (случайные/детерминированные mock-данные).

Прототип **не реализует**:
- реальный сетевой драйвер и перехват трафика;
- реальную аутентификацию/подписку (можно замокать статус);
- реальные серверы и маршруты;
- реальную поддержку/тикеты.

### 1.3 Термины
| Термин | Значение |
|---|---|
| Сервис (Service) | Приложение/игра/сайт, трафик которого маршрутизируется через Fixnet |
| Регион (Region) | Точка выхода трафика (например, Sweden, Germany) — один из 9 серверных узлов |
| WorldRegion | Широкий географический регион пользователя (один из 12 вариантов для онбординга) — не путать с Region |
| Маршрут (Route) | Сетевой путь между устройством и целевым сервисом через инфраструктуру Fixnet |
| Соединение (Connection) | Активная сессия передачи трафика конкретного сервиса |
| Мост (Bridge) | Резервный способ доступа к инфраструктуре при недоступности основного маршрута |
| Каталог (Catalog) | Предустановленный список из 19 сервисов с рекомендованными настройками |
| Режим соединения (ConnectionMode) | Приоритет качества: `default` / `fast` / `stable` / `secure` |

## 2. Общее описание системы

Fixnet не туннелирует весь трафик пользователя. Пользователь явно выбирает набор сервисов, для каждого из которых индивидуально настраивается регион выхода и параметры подключения. Всё остальное продолжает работать через обычное интернет-соединение напрямую.

Ключевая идея: **N сервисов → N независимых маршрутов**, работающих параллельно.

### 2.1 Основной жизненный цикл
1. Пользователь авторизуется (16-значный ключ, mock).
2. Онбординг: выбор широкого региона → коучмарк-тур по интерфейсу (можно пропустить).
3. На экране Services пользователь выбирает сервисы из каталога (мультиселект).
4. Опционально: настройка параметров каждого сервиса (регион, режим соединения, транспорт и т.д.).
5. Нажимает «Start selected» — активируется mock сетевой слой.
6. Приложение «маршрутизирует» выбранные сервисы (симуляция); Dashboard показывает SVG-топологию.
7. При сбоях (симулируемых): статус сервиса меняется в диаграмме; при autoBridge=true мост подключается автоматически.
8. Уведомления — контентные (обновления серверов, биллинг, новые сервисы); реально-событийные уведомления от движка не реализованы.

## 3. Сущности, атрибуты, состояния

### 3.1 User (Пользователь)

**Атрибуты:**
| Поле | Тип | Описание |
|---|---|---|
| id | string | Идентификатор |
| name | string | Отображаемое имя |
| email | string | Почта (mock) |
| subscriptionStatus | enum: `active`, `expired`, `trial` | Статус подписки |
| subscriptionExpiresAt | number (Unix ms) | Дата окончания подписки |
| homeRegion | string \| null | Широкий географический регион пользователя (выбирается при онбординге, не влияет на маршрутизацию) |

> **Архитектурное примечание:** Библиотека сервисов (`library`), аварийные мосты (`bridges`) и настройки приложения (`appSettings`) хранятся как поля верхнего уровня в store, а не вложены в User. Пресеты из прототипа удалены (см. §3.7).

**Состояния подписки:** `active → expired`, `trial → active`, `trial → expired`.

---

### 3.2 Service (Сервис)

Главная сущность приложения.

**Атрибуты:**
| Поле | Тип | Описание |
|---|---|---|
| id | string | Идентификатор |
| name | string | Название (ChatGPT, Discord, Steam...) |
| icon | string (emoji) | Иконка (emoji-символ; используется как fallback если нет SVG бренда) |
| category | enum: `ai`, `game`, `streaming`, `browser`, `messenger`, `other` | Тип сервиса |
| detectionMethod | enum: `domain`, `exe`, `game` (`exe`+`domain`+rules), `manual` | Способ определения трафика |
| domains | string[] | Список доменов (для web-сервисов) |
| includeSubdomains | boolean | Включать поддомены при domain-детекции |
| exePath | string \| null | Путь к exe (для программ/игр) |
| ipRange | string \| null | IP-диапазон (для ручных сервисов) |
| additionalRules | NetworkRule[] | Доп. сетевые правила |
| region | string (Region.id) | Выбранный регион выхода |
| enabled | boolean | Включен/выключен |
| encryption | enum: `on`, `off` | Шифрование |
| transportType | enum: `udp`, `tcp`, `mixed` | Тип транспорта |
| dnsMode | enum: `default`, `custom` | Использование DNS |
| connectionMode | enum: `default`, `fast`, `stable`, `secure` | Режим соединения (приоритет: скорость / стабильность / безопасность) |
| advancedSettings | object | Расширенные настройки (для опытных пользователей; в прототипе всегда `{}`) |
| isCustom | boolean | true — если создан пользователем вручную |
| status | enum: `inactive`, `connecting`, `connected`, `degraded`, `error` | Текущий статус соединения |
| addedFromLibrary | boolean | Добавлен из общей библиотеки или создан вручную |

**Состояния (жизненный цикл сервиса):**
```
inactive --(пользователь включает + Запуск приложения)--> connecting
connecting --(успех)--> connected
connecting --(таймаут/ошибка)--> error
connected --(деградация сети, mock-событие)--> degraded
degraded --(восстановление)--> connected
degraded --(потеря маршрута)--> error
error --(ручной retry / авто-retry)--> connecting
connected/degraded/error --(пользователь выключает сервис)--> inactive
```

**Правила определения трафика по категориям:**
- **Веб-сервис** → `detectionMethod: domain`, обязателен непустой `domains[]`.
- **Программа** → `detectionMethod: exe`, обязателен `exePath`.
- **Игра** → `detectionMethod: game`, требует `exePath` + `domains[]` + `additionalRules[]`.
- **Ручной сервис** → `detectionMethod: manual`, `isCustom: true`; при создании показывается предупреждение об ответственности пользователя за корректность настройки.

### 3.5 Route (Маршрут)

Формируется автоматически при включении сервиса; связывает Service с Region и текущим состоянием передачи.

| Поле | Тип | Описание |
|---|---|---|
| id | string | Идентификатор |
| serviceId | string | Ссылка на Service |
| regionId | string | Ссылка на Region |
| status | enum: `idle`, `active`, `degraded`, `unavailable` | Статус маршрута |
| latencyMs | number | Задержка (mock, обновляется периодически) |
| stability | number (0–100) | Индекс стабильности (mock) |
| usesBridge | boolean | Использует ли сейчас аварийный мост |

---

### 3.6 Connection (Соединение)

Активная сессия конкретного Route в моменте. По сути — снимок состояния маршрута, используемый для отображения в мониторинге и истории.

| Поле | Тип | Описание |
|---|---|---|
| id | string | Идентификатор |
| routeId | string | Ссылка на Route |
| startedAt | datetime | Время начала |
| endedAt | datetime \| null | Время окончания (если завершено) |
| qualityHistory | {timestamp, latencyMs, stability}[] | История качества для графика |

### 3.7 Preset (Пресет)

> **Статус в прототипе: удалён.** Функциональность пресетов (сохранение конфигурации, применение пресетов, список пресетов) была исключена из текущего прототипа. Сущность Preset, все связанные экшены и UI-компоненты отсутствуют. Функциональные требования FR-17/FR-18 и пользовательские сценарии 6–7 на данный момент не реализованы. Пресеты могут быть восстановлены в будущей итерации.

### 3.8 Bridge (Аварийный мост)

| Поле | Тип | Описание |
|---|---|---|
| id | string | Идентификатор |
| name | string | Всегда `Bridge-N` (порядковый номер) |
| status | enum: `available`, `connecting`, `connected`, `failed` | Статус |
| triggeredBy | string (serviceId) \| null | Какой **сервис** инициировал подключение моста (не routeId — поиск и создание мостов происходит на уровне serviceId) |
| isAuto | boolean | Подключается автоматически или по запросу пользователя |

**Логика активации:**
```
Route.status → unavailable
  → приложение пытается восстановить основной маршрут
    → неудача → предлагает Bridge (если isAuto=false) ИЛИ подключает автоматически (если isAuto=true)
      → Bridge.status: available → connecting → connected
        → повторная попытка Route → active (usesBridge=true)
```

## 4. Связи между сущностями (ER-обзор)

```
Store (top-level)
  ├── User 1 (профиль)
  ├── AppSettings 1
  ├── library: Service[]        (личная библиотека пользователя)
  ├── bridges: Bridge[]
  └── notifications: Notification[]

Service 1───1 Region            (текущий выбранный регион, через service.region = Region.id)
Service 1───* NetworkRule       (только для game/manual)
Service 1───1 Route             (routes[serviceId] — один маршрут на сервис)
Service 1───1 Connection        (connections[serviceId] — одна активная сессия на сервис)
Connection 1───* QualitySample  (история для графика)
Route *───1 Bridge              (опционально, если usesBridge; Bridge.triggeredBy = serviceId)
```

> Пресеты удалены (см. §3.7). Уведомления больше не связаны с конкретным сервисом (поле `relatedServiceId` удалено из схемы).

## 5. Функциональные требования (укрупнённо)

### 5.1 Библиотека сервисов
- FR-1: Приложение отображает предустановленный каталог сервисов с иконкой, категорией, рекомендованным регионом и режимом соединения.
- FR-2: Пользователь выбирает сервисы в экране Services (мультиселект) и запускает их кнопкой «Start selected».
- FR-3: Пользователь может создать ручной сервис; перед формой показывается информационный экран с рекомендацией обратиться в поддержку для публичных сервисов.
- FR-4: При выборе сервиса из каталога через клик по карточке сервис создаётся с `enabled=true` и сразу подключается, если маршрутизация уже запущена.

### 5.2 Настройка сервиса
- FR-5: Для каждого сервиса независимо настраиваются: включен/выключен, регион, шифрование, транспорт (`udp`/`tcp`/`mixed`), DNS-режим, режим соединения (`default`/`fast`/`stable`/`secure`), includeSubdomains, ipRange, расширенные сетевые правила.
- FR-6: Изменение параметров одного сервиса не влияет на другие.

### 5.3 Запуск и маршрутизация
- FR-7: По нажатию «Start selected» / «Reconnect with changes» выбранные сервисы переходят `inactive → connecting → connected` (с симулированной задержкой 800–2000 мс). С вероятностью 8% переход заканчивается ошибкой `error` с автоматическим retry через 4–8 с.
- FR-8: Остальной (не сконфигурированный) трафик считается «напрямую» и не отображается как управляемый.
- FR-9: Каждый активный сервис отображает независимый статус, регион, задержку и стабильность.
- FR-9a: `startWithOnly(serviceIds)` — запуск только указанных сервисов: все остальные enabled-сервисы отключаются. Используется при «Start selected» из Services и «Start this service only» из ServiceDetailModal.

### 5.4 Мониторинг
- FR-10: Главный экран показывает сводную картину: количество активных сервисов, средняя задержка, есть ли проблемы.
- FR-11: На детальном экране сервиса отображается график качества соединения (mock-история).
- FR-12: Периодически (симулированный таймер) состояние маршрутов может меняться (`connected → degraded → connected`, либо `→ error`), генерируя уведомления.

### 5.5 Уведомления
- FR-13: При смене статуса маршрута на `degraded`/`unavailable`/`error` создаётся Notification соответствующего типа.
- FR-14: Уведомление может содержать действие: показать альтернативный маршрут, подключить мост, перейти к сервису.

### 5.6 Аварийные мосты
- FR-15: При недоступности основного маршрута приложение предлагает подключить мост (или подключает автоматически, если так настроено).
- FR-16: После подключения моста маршрут помечается `usesBridge: true`, статус пытается вернуться в `active`.

### 5.7 Пресеты

> **Статус: удалены из прототипа.** FR-17 и FR-18 не реализованы. Функция сохранения/применения пресетов запланирована для будущей итерации.

### 5.8 Настройки приложения
- FR-19: Общие настройки (тема, автозапуск, поведение окна, DNS, регион по умолчанию) не привязаны к сервисам и хранятся в AppSettings.
- FR-19a: Настройки DNS хранят конкретные адреса серверов (`dns.current` + `dns.backups[]`), а не режим-enum.
- FR-19b: Секция Connection в Settings управляет аварийным мостом (`emergencyBridge`) и резервными мостами (`backupBridges`) по кодам доступа.

## 6. Пользовательские сценарии (User Flows) для прототипа

1. **Первый запуск** → авторизация (16-значный ключ, mock) → онбординг (5 стадий, можно пропустить на любом шаге):
   - **Welcome (без счётчика шагов):** заставка HeroBanner с кнопками «Get started» / «Skip onboarding».
   - **1/4 — Region step:** выбор широкого географического региона пользователя из 12 вариантов (не влияет на маршрутизацию; сохраняется в `User.homeRegion`).
   - **2/4 — Tour Home:** коучмарк поверх Dashboard с описанием Service Routing.
   - **3/4 — Tour Services:** коучмарк поверх экрана Services с описанием выбора сервисов.
   - **4/4 — Tour Selected:** коучмарк поверх панели выбранных сервисов («Got it» завершает онбординг).

2. **Выбор сервисов** → экран Services → мультиселект карточек каталога → «Start selected» → маршрутизация запускается, экран переходит на Dashboard.

3. **Настройка сервиса** → открыть карточку сервиса (иконка шестерёнки) → ServiceDetailModal → выбрать регион, encryption, transportType, connectionMode, dnsMode → изменения применяются сразу; при закрытии с несохранёнными изменениями — confirm-диалог.

4. **Запуск / остановка** → Dashboard: кнопки Start/Edit на карточке «Service Routing» → при запуске отображается RoutingDiagram с SVG-топологией маршрутов.

5. **Деградация сети** → симулированное ухудшение маршрута → статус сервиса меняется на `degraded`/`error` (отражается в RoutingDiagram) → при autoBridge=true мост подключается автоматически → маршрут восстанавливается с `usesBridge=true`.

7. ~~**Применение пресета**~~ — *удалено из прототипа.*

## 7. Требования к UI (для прототипа)

- Платформа: Windows desktop, фиксированное окно **1200×800px** (не resizable).
- Структура окна: Windows-style title bar (32px) + боковая навигация (220px) + область контента.
- **Боковая навигация:** Home (Dashboard), Services, Settings. Нижняя часть: кнопка-уведомления (открывает NotificationPanel), статус подписки.
- **Главный экран (Dashboard):**
  - Во время онбординга: заставка (HeroBanner welcome) → шаг выбора региона → коучмарки поверх экранов.
  - Когда маршрутизация не запущена: карточки «Service Routing» (с кнопками Start/Edit или Select services) и «Full Mode» (UI-placeholder, функция не реализована в прототипе).
  - Когда маршрутизация запущена: SVG-диаграмма топологии маршрутов (RoutingDiagram).
- **Экран Services:** мультиселект каталога сервисов (4 колонки, вкладки All/Games/Social/AI/Entertainment/Other/Custom, поиск), правая панель с выбранными сервисами и кнопками Start/Stop/Reconnect.
- **Модальные окна:** настройка сервиса (ServiceDetailModal), мониторинг сессии (ServiceSessionModal), форма ручного сервиса (CreateCustomServiceModal), информационный предэкран (ManualServiceIntroModal).
- **Уведомления:**
  - NotificationPanel — оверлей-окно: список уведомлений, «Mark all as read», «Delete all» с undo-тостом.
  - NotificationToastStack — стек тостов в правом нижнем углу (peek / expanded).
- Никаких реальных сетевых вызовов — все статусы, задержки и события генерируются mock-логикой (таймеры, псевдослучайные изменения) для тестирования флоу.

## 8. Нефункциональные требования (для прототипа)

- NFR-1: Прототип работает полностью на клиенте, без бэкенда.
- NFR-2: Состояние может храниться в памяти (не обязательно персистентно между перезапусками) — если нужна персистентность, использовать локальное хранилище.
- NFR-3: Симуляция сетевых событий должна быть настраиваемой (частота, вероятность деградации) для удобства тестирования флоу.
- NFR-4: UI должен четко отличать состояния `connected` / `degraded` / `error` / `inactive` визуально (цвет, иконка).

## 9. Ограничения прототипа

- Нет реальной аутентификации, подписки, платежей.
- Нет реального сетевого драйвера / перехвата трафика.
- Нет реальных серверов/регионов — используется статичный справочник.
- Нет реальной службы поддержки — «отправить запрос на добавление сервиса» может быть просто UI-заглушкой.
